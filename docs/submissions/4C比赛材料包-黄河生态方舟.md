# 4C 比赛材料包：黄河生态方舟

## 0. 推荐参赛定位

建议主报赛道：**软件应用与开发 - Web 应用与开发**。

理由：本项目的主体是一个 B/S 架构的生态监测与公众参与平台，包含地图可视化、数据管理、物种百科、观鸟记录、图像识别、科普图库、游戏化互动、后台审核与部署上线能力，最符合软件应用与开发类对“运行在网络、数据库系统之上的软件，提供信息管理、信息服务、算法应用等功能”的要求。

不建议主报物联网：目前移动端/APP更偏向拍照上传、定位和轻量交互入口，没有完整硬件感知系统或可展示实物设备，物联网赛道要求“可展示实物系统”，风险较高。

不建议主报大数据：项目有生态观测数据和空间数据治理能力，但当前数据规模与多源融合深度还没有达到大数据赛道对“数据集、实验分析、研究报告、海量多源数据处理”的强要求。

可作为支撑亮点强调：AI识别、生态空间数据治理、公众协同上报、科普传播、黄河流域生态保护应用价值。

## 1. 项目简介（约 600 字）

“黄河生态方舟”是一套面向黄河湿地鸟类保护与公众协同巡护的 Web 综合平台，项目以黄河流域生态保护和高质量发展、国家生物多样性保护、数字中国与美丽中国建设为背景，针对传统湿地鸟类监测中数据分散、公众参与门槛高、物种知识传播弱、管理端审核与展示链路割裂等问题，构建了“观测采集 - 数据治理 - 智能识别 - 地图分析 - 科普传播 - 互动参与”的一体化应用系统。

平台以 Django 和 Django REST Framework 为后端基础，结合 PostgreSQL/PostGIS 空间数据、Leaflet 地图、天地图底图、物种数据库和观鸟记录数据库，实现湿地区域、监测点位、监测样线、鸟类观测记录的可视化展示与后台管理。用户可以在 Web 端查看黄河湿地生态大屏、筛选观鸟记录、圈选区域生成鸟类数量热力图，也可以通过上报页面提交观测时间、地点、物种、数量、图片和描述。管理端可对物种、区域、样线、观测记录、图库和识别记录进行维护与审核，形成从数据采集到数据应用的闭环。

项目还集成了水鸟图像识别模块，使用检测模型与分类模型对上传图片进行鸟体定位和物种判断，并提供识别阈值设置，以适应不同图片质量和应用场景。围绕公众科普，平台建设了物种百科、鸟类图库、科普文章和多个湿地主题互动小游戏，既服务专业监测，也降低普通公众了解鸟类与参与生态保护的门槛。移动端/APP部分作为辅助入口，重点承担拍照上传、定位和轻量交互，核心管理、展示、分析和答辩演示能力集中在 Web 端。

整体而言，“黄河生态方舟”不是单一展示网页，而是一个具有真实数据结构、可运行后台、空间可视化分析、AI识别能力和公众参与机制的生态治理辅助系统。它将专业监测数据、社会化观鸟记录和科普传播连接起来，为黄河湿地鸟类保护提供数字化、可视化、可扩展的解决方案。

## 2. 用户说明

### 2.1 用户角色

**游客/公众用户**  
可以访问首页生态大屏、物种百科、鸟类图库、科普文章和互动游戏，了解黄河湿地鸟类资源、保护等级、分布习性和观测记录。

**观鸟爱好者/巡护人员**  
可以通过上报入口提交观鸟记录，包括物种、监测点位、观测时间、数量、图片和描述。移动端/APP主要作为辅助采集入口，负责拍照、定位与轻量上传。

**管理员/老师/项目维护者**  
通过 Django 后台管理物种信息、湿地区域、监测点位、监测样线、观测记录、图库图片、AI识别历史和用户积分。管理员还可以审核公众上报记录，保证数据质量。

**评委/答辩用户**  
重点体验首页大屏、热力图圈选、物种百科、图库搜索、水鸟识别和后台管理，理解项目从数据采集到生态辅助决策的完整链路。

### 2.2 普通用户操作路径

1. 进入首页生态大屏，查看湿地地图、监测点位、监测样线和观鸟记录。
2. 使用左侧图层控制切换底图、注记、监测点位、监测样线和观鸟记录。
3. 调整时间范围，筛选不同日期内的观鸟记录。
4. 点击地图上的观测点，查看物种、数量、区域、时间、保护等级占比和区域分布等信息。
5. 点击“热力圈选”，在地图上拖拽出区域，系统以南北向最小外接矩形生成鸟类数量热力图。
6. 进入“物种百科”，查看物种中文名、拉丁名、目科、保护等级、习性和图库入口。
7. 进入“图库”，按照物种名、保护等级筛选图片，查看鸟类影像资料。
8. 进入“科普文章”，阅读平台生成的湿地保护与物种科普内容。
9. 进入“水鸟识别”，上传鸟类图片，设置检测阈值和分类阈值，查看识别结果。
10. 进入互动游戏，如迁徙、湿地修复、湿地侦探等，以游戏方式理解生态保护知识。

### 2.3 管理员操作路径

1. 进入 `/admin/` 登录后台。
2. 在“物种信息”中维护中文名、拉丁名、目、科、保护等级、习性和封面图。
3. 在“监测点位”和“监测样线”中维护空间数据。
4. 在“观测记录”中查看、审核和修正公众上报数据。
5. 在“物种图库”中维护图片来源、作者、说明和精选图。
6. 在“模型识别记录”中查看 AI 识别历史。
7. 定期运行同步命令，补齐图库和物种百科图片。

常用维护命令：

```bash
python manage.py check
python manage.py migrate
python manage.py collectstatic --noinput
python manage.py sync_species_gallery
python manage.py backfill_species_wikimedia_images --skip-wikidata --sleep 0.05
```

## 3. 整体框架和结构说明

### 3.1 总体架构

项目采用典型 B/S 架构：

```text
用户浏览器
  ↓
前端页面层：HTML / CSS / JavaScript / Leaflet / Chart.js
  ↓
Django URL 路由层
  ↓
Django REST Framework API 层
  ↓
业务模型层：物种、区域、样线、观测记录、图库、用户、识别记录
  ↓
数据库层：PostgreSQL + PostGIS 空间数据
  ↓
文件与模型资源：media 图片、static 静态资源、YOLO 识别模型
```

### 3.2 前端功能层

首页生态大屏：`app_monitor/templates/index.html`  
负责展示天地图底图、监测点位、监测样线、观鸟记录、统计面板、记录弹窗和热力图圈选。

物种百科：`app_monitor/templates/species.html`  
展示物种卡片、保护等级、拉丁名、目科、习性、图库入口和详情弹窗。当前已处理物种图片兜底和同学名去重。

鸟类图库：`app_monitor/templates/species-gallery.html`  
展示物种影像库，支持搜索、筛选和图片来源展示。

科普文章：`app_monitor/templates/articles.html`、`article-detail.html`  
展示湿地保护、物种知识和平台自动生成的科普内容。

上报入口：`templates/report.html`  
用于公众或巡护人员提交观鸟记录。

水鸟识别页：`app_monitor/templates/app_monitor/bird_recognition.html`  
用于上传图片、设置检测阈值和分类阈值，并展示识别结果。

互动游戏页：`templates/bird-guess.html`、`bird-runner.html`、`migration.html`、`wetland-restorer.html`、`wetland-detective.html`、`floating-island.html`  
用于公众科普、生态教育和答辩展示互动性。

### 3.3 后端业务层

核心 Django 应用：`app_monitor`  
负责生态监测业务，包括物种、湿地区域、监测样线、观测记录、用户积分、图库、文章 API、首页视图和热点推荐。

AI 识别应用：`bird_recognition`  
负责图片上传、模型加载、鸟体检测、物种分类和识别结果返回。

核心模型：

```text
SpeciesInfo：物种信息
WetlandZone：湿地监测点位
MonitoringRoute：监测样线
ObservationRecord：观鸟记录
SpeciesImage：物种图库
AIDetectionResult：AI识别历史
UserProfile：用户积分档案
Product：积分商城商品
```

核心 API：

```text
/api/species/             物种百科数据
/api/species-images/      物种图库数据
/api/observations/        观鸟记录数据
/api/zones/               监测点位数据
/api/transects/           监测样线数据
/api/articles/            科普文章数据
/api/profiles/me/         用户信息
/bird/recognize/          水鸟识别接口
```

### 3.4 数据链路

1. 后台导入或维护物种、点位、样线和观测记录。
2. 用户通过上报页或移动端辅助入口提交观鸟记录。
3. 管理员审核记录，标记为通过或驳回。
4. 通过 API 将审核后的记录提供给首页地图、统计面板、热力图和弹窗。
5. 物种百科和图库从物种表与图库表读取信息，并通过图片补全命令完善物种影像。
6. AI识别模块接收用户图片，返回识别结果和置信度。
7. 科普文章与互动游戏承接公众教育和传播功能。

### 3.5 部署结构

服务器部署建议：

```text
Nginx：外部 HTTP 入口、静态文件代理、反向代理
Gunicorn：Django WSGI 服务
Django：业务应用
PostgreSQL/PostGIS：数据库
static_root：收集后的静态文件
media：上传图片、图库图片和识别图片
bird_recognition/yolo_model：detector.pt 与 classifier.pt
```

## 4. 亮点与创新点

### 4.1 专业监测与公众协同融合

项目不是只给专业人员使用，也不是单纯做科普展示，而是将巡护员、观鸟爱好者和普通公众纳入数据采集链路。公众上报经后台审核后进入平台数据池，形成“专业监测 + 社会协同”的生态治理闭环。

### 4.2 空间可视化与生态分析结合

首页将湿地区域、监测点位、监测样线、观鸟记录统一叠加到地图中，支持图层切换、时间筛选、记录弹窗和区域热力图。热力图功能支持用户圈选任意区域，系统自动按南北向最小外接矩形统计观鸟数量，直观呈现鸟类活动热点。

### 4.3 AI 图像识别嵌入业务流程

水鸟识别模块不是孤立模型演示，而是服务于观测上报、物种辅助判断和公众科普。系统支持检测阈值和分类阈值设置，使识别过程更透明，也方便在不同图片质量下调整模型敏感度。

### 4.4 物种百科与图库数据治理

平台建设了物种百科和图库系统，将物种中文名、拉丁名、目科、保护等级、习性、图片来源和观测记录关联展示。针对物种别名、同学名重复、图片缺失等真实数据问题，系统加入了图库同步、图片补全、同学名去重和搜索别名兼容逻辑。

### 4.5 Web 端为核心，移动端轻量补充

项目核心能力集中在 Web 端，包括管理、展示、分析、识别、科普和答辩演示。移动端/APP不强行承担复杂业务，而是作为拍照上传、定位和轻量交互入口，定位清晰，避免为了“全端”而牺牲系统稳定性。

### 4.6 生态教育与游戏化传播

项目提供鸟类猜图、迁徙、湿地修复、湿地侦探、浮岛等互动内容，适合在学校、科普馆、湿地公园和公众宣传场景使用。它把生态保护知识从静态文字转化为可体验的交互过程。

### 4.7 对国家战略的呼应

项目服务于黄河流域生态保护和高质量发展，体现生物多样性保护、生态文明建设、数字中国、美丽中国、公众参与式治理等方向。答辩时要强调：我们做的不是泛泛的鸟类网站，而是面向黄河湿地保护场景的数字化工具。

坦诚但主动：

3. 移动端目前偏轻量，后续可完善离线上报和巡护任务。
4. 可进一步加入趋势预测、异常预警和自动报告生成。

6. 进入水鸟识别，上传测试图，调整阈值并识别。
7. 进入后台，展示数据表和审核能力。
8. 用一句话说明游戏和科普模块是公众参与延展。

## 7. 队友速成说明：必须透彻理解的内容

### 7.1 一句话讲项目

“黄河生态方舟”是一个面向黄河湿地鸟类保护的 Web 平台，把观鸟记录、监测点位、物种百科、图库、AI识别、热力图分析和公众科普整合起来，帮助管理者看清数据，也帮助公众参与保护。

### 7.2 三句话讲价值

第一，它解决了观鸟和巡护数据分散的问题，让数据能统一上报、审核、管理和展示。  
第二，它用地图、热力图和统计弹窗把鸟类活动变得直观，能辅助识别鸟类热点区域。  
第三，它通过 AI 识别、物种百科、图库和互动游戏降低公众参与门槛，让生态保护不只停留在专业人员内部。

### 7.3 技术路线怎么讲

前端用 HTML、CSS、JavaScript、Leaflet 和 Chart.js 做地图、图表和交互。  
后端用 Django 和 Django REST Framework 做业务接口。  
数据库用 PostgreSQL/PostGIS 存物种、点位、样线和观测记录。  
AI 部分用水鸟检测模型和分类模型处理上传图片。  
部署上使用 Nginx + Gunicorn + Django。

### 7.4 为什么不是单纯网页

因为它有完整的数据模型、后台管理、API 接口、空间数据、用户上报、审核流程、AI识别和服务器部署，不是只展示静态页面。

### 7.5 为什么不主报大数据

可以这样答：  
“项目中确实有生态观测数据和空间数据治理能力，但当前作品更突出的是软件系统的完整性和应用落地。大数据赛道更强调大规模、多源数据集、实验分析和研究报告，因此我们选择软件应用与开发赛道，同时把数据治理作为系统亮点。”

### 7.6 为什么不主报物联网

可以这样答：  
“项目目前的移动端主要承担拍照上传、定位和轻量交互，尚未形成完整硬件感知系统。物联网赛道要求实物系统展示，因此我们不强行包装为物联网，而是把它定位为 Web 核心平台加移动采集辅助。”

### 7.7 AI 部分怎么讲才稳

不要夸大成“完全自动准确识别所有鸟”。  
正确说法：  
“AI识别模块用于辅助判断。系统先检测图片中的鸟体区域，再对裁剪区域进行分类，并允许用户设置检测阈值和分类阈值。它可以降低普通用户识别门槛，但最终数据仍可通过后台审核保证质量。”

### 7.8 热力图怎么讲

“用户在地图上圈选区域后，系统会根据圈选范围生成南北向外接矩形，并统计该范围内观鸟记录的数量，把记录密集程度渲染成热力图。它可以帮助我们快速发现鸟类活动热点和巡护重点区域。”

### 7.9 物种百科和图库怎么讲

“百科负责结构化知识，图库负责影像证据。每个物种关联中文名、拉丁名、目科、保护等级、习性、观测次数和图片。我们还处理了缺图补全、别名搜索和同学名重复问题，使页面更接近真实数据治理场景。”

## 8. 答辩常见问题与参考回答

### Q1：这个项目和普通鸟类科普网站有什么区别？

普通科普网站主要展示文字和图片。本项目有真实业务链路：用户上报观测记录，管理员审核，数据进入数据库，再通过地图、热力图、百科、图库和统计弹窗展示，同时还接入 AI 识别和互动科普，形成从采集到应用的闭环。

### Q2：AI识别准确率如何保证？

系统通过检测阈值和分类阈值控制识别结果输出，并将识别定位为辅助工具而不是最终裁决。重要观测数据仍进入后台审核流程，由管理员保证数据质量。后续会通过扩展训练集、优化模型和积累本地样本提升效果。

### Q3：数据来源是什么？

数据包括项目整理的黄河湿地物种信息、监测点位、监测样线、观鸟记录、图库资料以及用户上报数据。图库部分结合本地上传和开放图片来源，并保留图片来源字段，方便追溯。

### Q4：项目如何服务生态保护？

它可以帮助管理者看到鸟类出现的位置、时间、数量和热点区域，也可以通过公众上报扩大数据采集覆盖面。科普和游戏模块能提升公众参与意愿，从而让生态保护从“少数专业人员工作”变成“专业监测与公众协同”的过程。

### Q5：为什么选择 Web 平台？

Web 平台便于展示、管理、部署和跨设备访问，适合答辩演示和实际推广。移动端目前作为辅助入口承担拍照和定位，不把复杂管理功能放在手机端，能保证核心业务稳定。

### Q6：项目未来怎么扩展？

未来可以扩展更多湿地区域和鸟类数据，接入更多巡护任务，加入趋势预测、异常预警、自动报告生成、离线上报和多端协同，并进一步优化 AI 模型性能。

## 9. 项目申报书可用摘要

本项目围绕黄河湿地鸟类保护场景，设计并实现了一套集观测上报、后台审核、空间可视化、AI识别、物种百科、图库科普和互动传播于一体的 Web 平台。系统通过 Django、Django REST Framework、PostgreSQL/PostGIS、Leaflet 和水鸟识别模型构建完整业务闭环，实现湿地监测点位、监测样线、观鸟记录和物种信息的统一管理与可视化展示。平台支持用户上报观鸟记录、管理员审核数据、地图图层切换、区域热力图分析、物种详情查询和鸟类图片识别，同时通过科普文章与互动游戏提升公众参与度。项目体现了黄河流域生态保护、生物多样性保护和数字化治理的融合应用价值，具有较强的软件完整性、实际应用场景和推广潜力。
